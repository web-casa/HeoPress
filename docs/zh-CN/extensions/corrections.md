# 纠错报告（`heopress-corrections`）

公开纠错表单、审核队列、文章上的更正记录与结构化数据。它是第一个直接面向读者的官方插件
（见 [官方插件 backlog](../../backlog/official-plugins.md) 第 1 项与 [ADR-0015](../../decisions/ADR-0015-plugin-boundary-and-extension-points.md)）。

## 它做什么

三步，全部在站点自己的数据里：

1. **读者提交**：一个公开表单接口 `/_ext/heopress-corrections/report`，把页面路径、引用原文、建议更正与可选的
   留言/姓名/邮箱写成一条**草稿**报告，放进私有集合 `heopress_corrections__reports`；
2. **运营者审核**：在 Studio 的报告集合里把审核状态 `status` 改成 `accepted` 或 `rejected`；
3. **公开记录与更正块**：接受后生成一条**草稿**更正记录 `heopress_corrections__notices`，运营者编辑并发布它；
   发布使记录出现在 `/corrections` 与 `/corrections/:slug`，并在被更正文章的正文末尾留下一个更正块。

一份报告最多产生一条更正记录；审核与写入都不需要邮件、外部服务或额外配置。读者永远看不到队列里的报告，
只有运营者发布过的记录才是公开的；记录一旦公开就会一直留在站点的公开内容里，直到运营者取消发布或删除它。
这也是这个插件与「联系表单」的根本区别：联系表单把信寄给运营者，纠错报告把结论留给读者。

## 安装与批准

在后台的扩展页安装官方插件 `heopress-corrections`，确认它声明的能力并启用。它不申请 `http:fetch`、`secrets`、
`ai` 或 `jobs`，也不声明 `prePublishHooks`，所以它不会因为自身加载失败而挡住任何人的发布。

安装会把两个集合建成站点自己的表，机器名以 `heopress_corrections__` 开头；卸载或禁用后集合与数据保留，
重新启用即继续使用。插件还在后台加了两个页面：一个列出每一次「报告 → 记录」的审核决定（报告、记录、文章、状态），
一个放两个设置项。能力批准后不需要再配置任何东西；如果站点还没有可用的公开模板，先确认主题能渲染插件路由，
再让读者看到表单。

## 读者看到的表单

表单由站点自己的页面提交到 `/_ext/heopress-corrections/report`。宿主先校验来源（只有本站已批准的来源可以提交），
再校验请求体不超过 `8 KiB`、同一客户端地址每分钟不超过 `5` 次。表单本身不随插件提供：站点在自己的页面里放几个
输入框并提交到这个地址即可，字段名与上表一致。运营者不需要给表单加验证码或额外的反垃圾服务——限制、蜜罐与
中性答复都在插件这一侧。

| 字段 | 必填 | 上限（字符） |
|---|---|---|
| 页面路径 | 是 | 512 |
| 引用原文 | 是 | 1000 |
| 建议更正 | 是 | 2000 |
| 留言 | 否 | 2000 |
| 姓名 | 否 | 120 |
| 邮箱 | 否 | 254 |

页面路径必须是本站路径：以 `/` 开头，不能是外站地址、`..` 段、查询串、片段或保留的 `/_` 前缀。
读者把浏览器地址栏里的整条链接粘进来是最常见的错误，所以站点应当在表单旁写一句「只填路径部分（从 / 开始）」；
即使读者粘了整条链接，接口也只会返回字段错误，不会因此把外站地址存进记录。引用、更正、留言与
姓名里的 `<`、`>` 会被**拒绝**（不静默清洗），控制字符与双向覆盖字符会被移除。

表单里有一个对读者不可见的 `website` 字段：被填写时，提交会被丢弃，答复与成功**完全相同**。所有合法提交、
重复提交与蜜罐命中的答复都是同一句话，既不确认页面存在，也不确认报告已记录——接口从不解析页面路径指向的条目。

## 审核：一个状态字段

打开报告集合（`heopress_corrections__reports`），在条目表单里把 `status` 改成 `accepted` 或 `rejected` 并保存。
这就是全部审核动作，不需要第二套界面。报告条目以草稿创建，读者看到的内容不会因为提交而公开；
运营者可以在条目里补写、删减引用与更正，但请保留报告 id 与页面路径，它们是记录与正文块的依据。

- `accepted`：插件创建一条**草稿**更正记录，标题取目标文章标题（找不到文章时取页面路径），路径段由报告 id 派生；
- `rejected`：什么都不发生，报告留在队列里，可以随时删除；
- `pending`：什么都不发生。

Studio 的「发布」按钮只写条目的核心状态（`draft`/`published`），它不是审核决定；报告条目一律以 `draft` 创建，
所以按发布按钮既不是接受也不是拒绝。

## 文章上的更正块

更正记录**发布**时，插件在被更正文章的正文末尾追加一个块。运营者应当先在记录里把标题、引用与更正改到可以公开
的程度，再点发布：记录页是公开的，正文块也会立刻出现在文章上。如果发现记录写错了，取消发布即可让块从文章上消失，
改好后再发布一次。

```html
<aside data-heopress-correction="r_example"><p><strong>Correction</strong> (2026-11-14): The bridge was built in 1989.</p><blockquote><p>The bridge was built in 1998.</p></blockquote></aside>
```

块的开头文字由设置 `marker_label` 决定（默认 `Correction`），日期取记录的更正日期。行为如下：

- 同一个报告 id 在正文里**只会有一个块**：重复的事件、再次发布、以及运营者在块内或块外的编辑都不会产生第二块，
  也不会覆盖运营者改过的文字；
- 取消发布或删除记录时，只移除该报告 id 的块，其余正文不动；
- 站点设置 `write_body` 关闭时，插件不写正文，记录仍然照常公开（更正只存在于记录页）；
- 目标文章没有正文字段时不动它；文章已不存在时记录仍然创建，只是没有可写的地方。

写入走正常的条目写入路径：新版本、修订、变更事件、缓存失效、发布守卫与其他插件的发布前检查都会执行。
公开页面会丢弃块的外壳与 `data-heopress-correction` 属性（与术语表链接同策略），但保留更正与引用的文字。

## 门禁检查

插件声明了一个针对文章的门禁检查 `notice-links`：正文里每个更正块都必须指向本站点一条**已发布**的更正记录。

- 没有更正块：通过；
- 每个块都指向已发布记录：通过；
- 块指向的记录不存在、仍为草稿、或块上的 id 不像报告 id：**阻止**（证据里列出缺失、未发布或格式非法的标记）；
- 读不到本站点的记录：**待复核**，不猜测通过。

要在发布前看到这个结论，用 Studio 的「运行门禁」或 AI 写入路径；**人工直接发布文章不会运行质量门禁**，
因此手工发布一篇指向未发布记录的文章不会被拦下。这是有意的取舍：内容插件不应因自身故障阻断全站发布。
被阻止时，运营者有两个正当的修法：把对应的更正记录发布出来，或者把文章里那段块删掉（如果这条更正不该公开）。
不要为了「让门禁通过」而把记录改成已发布却不核对内容——记录页是读者能看到的公开承诺。
如果一条更正已经不再成立（例如文章又被改对了），正确的做法是删除记录并让块随之消失，而不是留着一条过时的公开记录。

## 公开范围与结构化数据

- `/corrections` 列出本站已发布的更正记录，`/corrections/:slug` 是记录页；Classic 与 Astro 两个引擎都有模板；
  草稿没有页面，也不进 sitemap、feed 或页面数据。
- 记录页贡献一个 `CorrectionComment` 结构化数据节点（schema.org 对「对某个 CreativeWork 的更正」的定义），
  文本取更正内容、日期取更正日期、主题是被更正的页面。
- 报告集合没有任何公开页面；报告者姓名、邮箱、留言与记录的 `report_id`/`article_id` 都是隐藏字段，不出现在公开输出里。
- 列表页按发布时间倒序列出记录，分页大小是 50；记录页的规范地址、标题与描述由核心按站点设置生成，
  插件只提供模板与结构化数据节点，所以站点换域名或改语言前缀时不需要改插件。
- 记录进入 sitemap 与 feed 的方式与其他内容条目一致：发布即可见，取消发布即消失，草稿从不出现。

## 个人数据与保留

| 数据 | 是否公开 | 保留 |
|---|---|---|
| 页面路径、引用、更正 | 记录发布后公开 | 随记录删除 |
| 姓名、邮箱、留言 | 否 | 随报告删除 |
| 决定账本（只有 id） | 否 | 随站点删除 |

邮箱只用于运营者联系报告者这一人工动作：插件不发确认邮件，也不把它写进日志、公开页面或结构化数据。
宿主的接口错误日志只记插件名、错误码与计数，不记请求体；插件的订阅失败会记在扩展运行记录里，同样不含字段值。
报告与记录都是普通条目，删除报告即删除其个人信息；保留与删除策略见
[ADR-0013](../../decisions/ADR-0013-data-retention-and-deletion.md)。两个引擎的模板与
[简报分节](briefing-sections.md) 一样只使用清单里声明的模板上下文。

## 已知限制

1. 人工直接发布文章不运行质量门禁，`notice-links` 只在门禁路径上生效；
2. 文章页上没有 `CorrectionComment` 节点：为每篇文章聚合多条更正需要「核心 Schema 贡献」契约（backlog 待补），
   本插件不自造一个假的字段；
3. 结构化数据里的被更正页面是站点相对路径（清单无法计算站点 origin）；
4. 文章按页面路径的最后一段解析（先当 id、再当 slug），多语言共享 slug 时可能命中另一语言的文章；
5. 一份报告只有一条更正记录：拒绝后再次接受不会创建第二条，应编辑已有记录；
6. 记录取消发布再发布会按记录字段重建正文块，块内运营者的改写会丢失（块外的编辑不受影响）；
7. 清单的标签是单字符串，所以集合、字段与设置的标签是中英双写，公开路由标题只有英文。
