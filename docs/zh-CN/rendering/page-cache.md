# 页面缓存与失效

渲染服务缓存渲染好的页面，内容或主题变化后立即生效，不依赖变更事件是否送达。

实现：`apps/site-classic/src/cache.ts`（缓存键、两级缓存、清理）、`apps/site-classic/src/app.ts`（请求流程）、
`apps/cms/src/services/rendering/render-cache-consumer.ts`（变更事件消费者 `render-cache-invalidation`）。

## 怎样保证不返回旧页面

每个站点有两个渲染版本号（`lumibase_site_render_versions`），每篇公开条目还有自己的渲染版本号（`lumibase_public_items.render_version`），都取自同一个只增不重复的序列，
并且都在变更的**同一事务**内递增（公开投影的刷新与主题指针都经投影闸门，`apps/cms/src/services/site-network/public-projection.ts`）：

| 版本号 | 何时递增 |
|---|---|
| 站点 `version` | 站点公开输出的任何变化 |
| 站点 `structure_version` | 可能改变站点**任何**页面的变化：内容设置、SEO 设置、站点身份、域名、站点名称、字段与集合、扩展、主题发布与回滚、根文件、重定向；分类、标签、作者条目的变化（文章页的面包屑与作者取自它们）；路径以 `.md` 结尾的条目（它可能占用另一页面的 Markdown 副本地址）；整站重建 |
| 条目 `render_version` | 该条目的公开行被写入，或它的语言切换（`lumibase_public_alternates`）变化 |

每个缓存条目记下生成它时的版本号（与页面数据读自同一只读快照），只有这些版本号仍是当前值时才会被使用：

- **文章页**（`item` 类页面，含插件条目路由）：主题版本、站点 `structure_version` 与该条目的 `render_version` 都未变。发布或修改**另一篇**文章不会让它失效；
- **其他回答**（首页与列表分页、分类/标签/作者页、搜索、404、410、301、sitemap、feed、`llms.txt`、Markdown 副本）：主题版本、`structure_version` 与站点 `version` 都未变。
  任何文章的变化都会让它们重新生成。

所以发布一篇新文章只让该文章的地址（此前缓存的 404）、各列表与归档页、首页、feed 与 sitemap 重新生成，其余文章页继续命中缓存；
主题、设置等站点级变化仍让整站失效。版本号递增与变更同事务，因此：

- 变化后，旧条目不会再被使用，下一次请求按新数据渲染——不需要等待任何事件；消费者停摆时也一样。
- 旧数据不会以新版本号存入缓存（数据与版本号来自同一快照）。
- 变更事件与内容写在同一事务（P04 outbox）：事件写入失败时，内容、公开投影与版本号一起回滚，不会出现“内容已变、版本未变”。

## 缓存键与内容

| 组成 | 说明 |
|---|---|
| 模式 | 只有 `public`：预览从不进入缓存，代码也无法为预览生成键 |
| 站点、请求主机、路径 | 别名主机与语言入口主机各自独立；语言由主机与路径决定（三种语言入口都体现为主机或路径），不单列 |
| 规范化查询参数 | 只有 `page`（非数字统一为一个 404 条目）与搜索页的 `q`（去首尾空白，最多 200 字符）；其他参数（如 `utm_*`）不影响输出，也不进入键 |

版本号不在键中，而是与条目一起保存（见上节）；每个地址只保留一行，较新快照生成的回答替换较旧的。

缓存 200、301、404、410 的响应；301 存储时去掉请求自带的查询，返回时再拼上本次请求的查询。503（重建中、渲染池已满）与 500（主题出错）不缓存，
响应带 `Cache-Control: no-store`。

预览（`docs/zh-CN/rendering/preview.md`）只在预览来源上提供，既不查也不写缓存，响应 `Cache-Control: no-store, private`。

两级：进程内 LRU（默认 64 MB，`HEOPRESS_RENDER_CACHE_MB`）与数据库表 `lumibase_render_cache`（所有渲染进程共享，渲染角色可读写；条目最多保留 1 天）。
响应头 `x-cache` 说明来源：`hit`（本进程缓存）、`hit-shared`（共享层，随后也放入本进程）、`miss`（本次渲染）。
命中时只执行一条查询（站点的版本号、当前主题版本、重建标记，以及共享层的行或本进程条目所依赖的条目版本号）：站点范围设置（`app.site_id`，事务内有效）也在这条语句中，所有值都是绑定参数、不拼进 SQL 文本，语句在每个连接上只准备一次；一次往返，不另开显式事务，设置随语句的隐式事务结束；
使用单独的连接池（`HEOPRESS_RENDER_LOOKUP_DB_POOL`），不读页面数据、不进渲染线程池，因此不会排在未命中的渲染之后。
域名记录在本进程内最多记住 1 秒（`HEOPRESS_RENDER_HOST_MEMO_MS`，最多 2 秒，P06 设计 R8 允许的进程内记忆），版本号从不记忆：每次命中都核对当前版本。站点等待重建时不使用任何缓存条目（返回 503）。
性能基线见 `docs/benchmarks/p06-classic.md`。
数据库表只收数量由站点内容决定的回答——内容页（200）与已删除页（410）；404、别名跳转与搜索结果只放在进程内缓存，任何请求都无法让表无限增长。
搜索页按解码后的路径识别（`/%73earch/` 同样以 `q` 区分）。

## HTTP 头

- `ETag`：弱校验值（状态、目标地址与正文的哈希）；`If-None-Match` 匹配时 200 页面返回 304。
- `Cache-Control: public, max-age=0, must-revalidate, s-maxage=5`：浏览器每次都校验，共享缓存（CDN）最多保留 5 秒。
- `X-Cache: hit | miss`：便于排查。

## 清理

- CMS 的 `render-cache-invalidation` 消费者在内容、路由、重定向、内容设置、字段与集合、翻译组、主题的变更事件到达时，删除该站点已不能使用的缓存行
  （`staleRenderCacheRows`，`packages/database/src/schema/public-projection.ts`：版本号不再是当前值的行）。
- 渲染服务每 60 秒清理一次过期与不能再使用的行：分批删除，整个集群同一时刻只有一个进程在清理（advisory lock）。

二者只负责释放空间，正确性不依赖它们。

## 信任边界

渲染角色可以写入任何站点的缓存行。所有站点由同一个渲染进程、同一个数据库角色服务，攻破它本来就能为任何站点返回任意内容，缓存没有增加这种能力；
主题模板在 worker 线程中执行，不持有数据库连接。怀疑渲染进程被入侵时，轮换渲染角色密码并清空 `lumibase_render_cache`。
