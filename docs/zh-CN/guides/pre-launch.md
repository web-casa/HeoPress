# 上线前验收清单

在把 HeoPress 用于真实站点、并向他人承诺可用性之前，跑完这份清单。它只包含**本仓库无法替你完成**的验证：
自动化门禁能证明的（安装、最小部署、升级路径、备份套件、权限隔离、渲染正确性）都在 CI 里，每次提交都跑。

清单的每一项都要留下记录（日期、环境、命令、结果），写进你的运维日志。没有记录就视为没有做。

## 1. 容量：在真实 VPS 上重跑基准

`docs/benchmarks/` 里的数字来自开发机上用 Docker 限额**模拟**的 2 vCPU / 4 GB，文档自己也写明不能当作容量规划依据。
在你要使用的机型上重跑一遍：

```bash
export COMPOSE_PROJECT_NAME=hpbench POSTGRES_PORT=56433 CMS_PORT=11989 SITE_PORT=12027 BENCH_OUT=/tmp/bench-p06
# CMS 端口、渲染服务端口、每站文章数
docker/scripts/bench-p06-classic.sh 11989 12027 1000
```

通过标准（与 design 的目标一致）：未命中 p95 **< 300 ms**，缓存命中 p95 **< 30 ms**，且每个阶段 0 个失败请求、
`x-cache` 层级符合预期。记录机型、核数、内存、磁盘类型与实测 p50/p95/p99、渲染服务 RSS 峰值。

判定要点：如果命中 p95 超过 30 ms，先看数据库限额是否被打满（基准里 postgres 在 0.6 核时限流），
再决定是加核还是加缓存；不要用「开发机更快」解释差异。

## 2. 升级：在副本上预演一次

`heopress upgrade` 会依次做兼容检查 → 备份 → **在数据库副本上预演迁移** → 维护窗口冻结写入 → 最终备份 → 迁移 →
切换应用 → 冒烟 → 开放写入，但预演通过不等于你的库没问题：插件、自定义集合与真实数据量都可能暴露预演没覆盖的情况。

```bash
# 先确认你这一版的参数
heopress upgrade --help
```

在**生产库的副本**上完整走一遍（副本可以是 `heopress backup restore` 出来的实例），记录：耗时、维护窗口长度、
预演是否通过、冒烟是否通过。若预演失败，升级不会进入维护——把失败信息留着，那是你唯一能安全试错的机会。

**新版本一旦开放写入就不能回滚**：恢复旧备份会丢掉之后写入的数据。升级前先确认你接受这一点。

## 3. 备份与恢复：演练，而不是只开启

```bash
# 立即做一份
heopress backup run
# 校验清单与可读性
heopress backup verify
# 恢复到临时实例并检查
heopress backup drill
```

通过标准：`verify` 无错误、`drill` 能恢复并完成检查、恢复后的站点与文章数量与你预期一致。**密钥要单独保存**——
丢失加密密钥，备份等于没有。备份与恢复的完整说明见[备份与恢复](../operations/backup-restore.md)（中文）。

如果你只做一件事，就做这一件：没有演练过的备份不是备份。

## 4. 安全姿态：读一遍例外清单

`security/exceptions.json` 里每一条都是**我们已知但接受**的风险，不是已修复的问题。上线前读一遍，确认你能接受：

- 每条都有 `reason` 与 `reviewBy`；到期未复评会让安全扫描变红，这是设计好的提醒；
- 当前主要在 postgres 基础镜像的 krb5 库（Debian 未修复、KDC 侧问题，镜像不跑 KDC）；
- 复核依赖审计与镜像扫描的最新结果，不要只看「上次是绿的」。

同时确认：站点域名已验证、TLS 由 Caddy 正常签发、`HEOPRESS_REQUIRE_APP_ROLE` 为 true（应用以受限角色连库）。

## 5. Go / No-Go

| 项 | 通过判据 | 记录 |
|---|---|---|
| 容量 | 未命中 p95 < 300 ms、命中 p95 < 30 ms、0 失败 | 机型与实测数值 |
| 升级 | 副本预演与冒烟通过 | 耗时与维护窗口 |
| 备份 | `verify` 与 `drill` 通过 | 恢复后的数量核对 |
| 安全 | 例外清单已读、审计与镜像扫描无未处理项 | 复核日期 |
| 回滚 | 明确知道「开放写入后不能回滚」并接受 | 决策人 |

五项都有记录，才算可以对外承诺可用性。缺任何一项，都只能说「可以部署试用」。
