## 中文

### 构建沙箱：让第三方主题可以在不信任的前提下运行

安装第三方或市场来源的 Astro 主题，意味着构建期会执行别人写的代码。以前的构建是宿主上的一个子进程：它能读宿主文件、
能任意外联、能用光内存与进程表。设 `HEOPRESS_ASTRO_BUILD_SANDBOX=required` 后，构建改在**一次性容器**里：

- **只读根文件系统**，只挂载构建输入（只读）与输出（可写），没有第三个宿主路径；
- **构建期无网络**（`--network none`）：页面数据改为只读文件输入，依赖必须预装在模板里；
- **丢弃全部能力**、`no-new-privileges`、cgroup v2 限制 CPU/内存/进程数，并有墙钟上限；超时按容器名终止并清理；
- 运行时、套接字、镜像或 cgroup 不可用时**构建失败并给出修复说明**，绝不静默回落到子进程——否则「沙箱已启用」就是一句谎话。

不设这个变量时行为与之前完全一致，现有部署不需要改动。

### 配套：构建镜像与自包含模板

- `docker/astro-build/`：Node 24、非 root 用户的构建镜像（依赖来自挂载的模板，所以镜像很小，也不需要网络）；
- `scripts/prepare-astro-template.mjs`：产出部署要挂载的**自包含**模板——自带依赖存储、已编译的 `@heopress/contracts`、
  本地 `tsconfig`，并把 `.astro` 指向计划挂载的缓存 tmpfs；结束时自校验，入口解析不了就拒绝交付；
- `/health` 新增 `astroBuild: { required, available, reason }`：启用时读构建用的同一个探针，探针自身故障不会显示为健康。

### 两个真机才暴露的缺陷（已修）

我们在一台 Proxmox VE 宿主机上建了 AlmaLinux 10 虚拟机，用**与生产完全相同的参数**跑 rootless Podman 5.8：

1. **SELinux**（AlmaLinux 默认 Enforcing）：bind 挂载不带 `:z` 时写产物被拒绝（`EACCES`），**与 uid 无关**，是
   `user_home_t` 与 `container_t` 冲突。计划现在固定给两个挂载加 `:z`（无 SELinux 的主机忽略）。
2. **rootless 运行时的 uid**：容器 root **就是**发起构建的宿主用户，所以构建以 `0:0` 运行；传宿主 uid 会映射到**从属 uid**，
   输出目录反而不可写。rootful 运行时仍使用专用构建用户——由 `podman info` 的 `Host.Security.Rootless` 决定。

第一条会让任何 RHEL 系客户端构建**直接失败**，第二条会让 rootless 部署**永远写不出产物**；两者在本地的 Docker
（rootful、无 SELinux）上都测不出来。

**另有一条部署结论**：LXC 容器里跑不了 rootless Podman（`newuidmap: write to uid_map failed`），构建宿主必须是 VM 或裸机。

### 边界

沙箱挡的是**构建期逃逸为宿主控制**（读密钥、写宿主、外联、耗尽资源），不替代主题包本身的供应链措施（来源与签名、
`--ignore-scripts`、产物 CSP）。gVisor 只需把 `HEOPRESS_ASTRO_BUILD_RUNTIME` 设为 `runsc`，但尚未实测。

## English

### A build sandbox: third-party themes without trusting them

Installing a third-party Astro theme means running someone else's code at build time. A build used to be a child process on
the host: it could read host files, reach any address, and exhaust memory and the process table. With
`HEOPRESS_ASTRO_BUILD_SANDBOX=required` a build runs in a **throw-away container**:

- **read-only root filesystem**, with only the build's input (read-only) and output (writable) mounted — no third host path;
- **no network during the build**: page data becomes a read-only file input, and dependencies must be pre-installed in the template;
- **all capabilities dropped**, `no-new-privileges`, cgroup v2 limits on CPU, memory and pids, plus a wall-clock deadline; a
  timed-out build is killed by container name and cleaned up;
- when the runtime, socket, image or cgroups are unavailable the build **fails with a repair**, never silently falling back to
  the child process — otherwise "the sandbox is on" would be a lie.

With the variable unset, nothing changes; an existing deployment keeps building.

### The image and the self-contained template

- `docker/astro-build/`: a Node 24 image with a non-root user (dependencies come from the mounted template, so the image stays
  small and needs no network);
- `scripts/prepare-astro-template.mjs`: produces the **self-contained** template a deployment mounts — its own dependency store,
  the compiled `@heopress/contracts`, a local `tsconfig`, and `.astro` pointed at the cache tmpfs the plan mounts. It verifies
  the result and refuses to deliver a template whose entry points do not resolve;
- `/health` gains `astroBuild: { required, available, reason }`, read from the same probe a build uses; a broken probe never
  reads as healthy.

### Two defects only a real machine showed

We built an AlmaLinux 10 VM on a Proxmox VE host and ran rootless Podman 5.8 with **the same arguments production uses**:

1. **SELinux** (AlmaLinux enforces by default): a bind mount without `:z` is refused on write (`EACCES`) — nothing to do with the
   uid, it is `user_home_t` versus `container_t`. Both mounts now carry `:z`; hosts without SELinux ignore it.
2. **The uid under a rootless runtime**: the container's root *is* the invoking host user, so the build runs as `0:0`. Passing the
   host uid maps to a **subordinate** id and the output directory becomes unwritable. A rootful runtime keeps a dedicated build
   user; the probe asks `Host.Security.Rootless` and the runner chooses.

The first would fail every RHEL-family deployment outright, the second would make every rootless deployment produce nothing —
and neither is visible on a local Docker (rootful, no SELinux).

**One more deployment fact:** rootless Podman does not work inside an LXC container (`newuidmap: write to uid_map failed`), so a
build host must be a VM or bare metal.

### The boundary

The sandbox stops **build-time escape into host control** (reading secrets, writing the host, reaching the network, exhausting
resources). It does not replace supply-chain work on the theme package (provenance and signatures, `--ignore-scripts`, CSP on the
artifact). gVisor is one configuration away (`HEOPRESS_ASTRO_BUILD_RUNTIME=runsc`) but has not been measured yet.
