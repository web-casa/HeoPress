# HeoPress v1.0.0

> 状态 / Status: **草拟中，尚未发布 / being drafted, not released.** 日期 / Date: TBD.

[中文](#中文) · [English](#english)

## 中文

HeoPress 是面向 10–100 个独立域名站群的 AI 原生开源 CMS。v1.0.0 是第一个正式版本：一个实例管理多个站点，
采集、翻译、改写与质量门禁由确定性流程和受控的 AI 完成，外部 Agent 经 MCP 按用户、按站点授权接入。
HeoPress 由 LumiBase（Apache-2.0）硬分叉而来，详见 `UPSTREAM.md`。

文档入口：`docs/zh-CN/guides/index.md`（用户、开发者、运维三本指南）。

### 主要功能

- **站群**：一个实例多个独立域名站点；每站预设集合、语言、时区、按集合固定链接、重定向导入、编辑策略；域名验证与按需 TLS；
  跨站点、跨域名的翻译组与 hreflang；赞助内容的统一标记与披露。
- **Studio**：Carbon 设计的管理后台，八个模块（概览、内容、站点、SEO / GEO、AI 流量、审计、日志与监控、设置），中英双语；
  三栏文章编辑器、审稿工作台、签名预览。
- **渲染**：Classic 引擎（一个进程服务全部站点、Liquid 运行时主题、沙箱、按版本发布与回滚、三个起步主题）；
  Astro 静态引擎，产物可部署到自有服务器、Cloudflare Pages、Vercel、Netlify；Git 快照。
- **SEO / GEO**：canonical、hreflang、JSON-LD、分片 sitemap、`llms.txt`、Markdown 副本、IndexNow、AI 爬虫策略；
  站点审计、站内链接图、变更影响预览、AI 流量分析。
- **内容采集**：RSS / Atom、sitemap、列表页与 URL 信源；来源授权与使用方式；robots.txt、按主机限速与 SSRF 防护；
  外部采集服务降级链；精确与近似去重、同一事件聚合。
- **AI 流水线**：区块级翻译与增量重译、改写、撰写；质量门禁；按信任等级的自动发布、否决窗口与发布节奏；
  逐次调用账本、站点预算、限流与熔断；提示词工作台。
- **Agent 协作**：MCP 端点（OAuth 2.1、个人访问令牌、按站点与工具组授权）；批量操作计划与人工审批；内容分支与冲突感知合并；
  六个官方 Skills；后台与 IM / Webhook 通知。
- **扩展**：Extension SDK（Apache-2.0）、能力沙箱与管理员批准、只加载签名插件包；内容、运行时、流水线扩展点与发布前否决钩子；
  术语表参考插件；通用导入包与 Astro 站点导入、URL 对照。
- **运维**：一条命令安装；内置备份（全量 + 增量、SHA-256 清单、加密、保留、每周恢复演练）与单站点导出；
  `heopress upgrade`（预演、写入冻结、最终备份、失败恢复）；数据保留与删除账本；插件 codemod。

### 运行要求

- 一台 VPS（Ubuntu 24.04 + Docker Compose）；最小 2 vCPU / 4 GB。
- PostgreSQL 18（官方数据库镜像带 pgvector 与 zhparser）；Node.js 24（从源码构建时）。
- Redis、MinIO、MeiliSearch、imgproxy 都不是必需组件。

### 从 LumiBase 迁移

- 包名 `@lumibase/*` 改为 `@heopress/*`，环境变量前缀 `LUMIBASE_*` 改为 `HEOPRESS_*`（旧前缀会导致启动失败）；数据库标识的 `lumibase_` 前缀保留。
- 上游的 Cloudflare Workers 运行时已删除，只支持 VPS / Docker。
- 插件 API 的破坏性变更：运行 `heopress-ext codemod --only lumibase-to-heopress` 自动转换包名、清单文件名与 `compatibleWith` 字段，其余项目报告为人工步骤。
  插件改为能力沙箱模型：原有的 `db:read`、`db:write`、`env:read` 等能力不再存在。

数据库角色（安全复查 S-5）：

- Docker 部署中，CMS 与 worker 以非所有者的应用角色 `heopress_app` 连接数据库，渲染服务以 `heopress_render` 连接。
  所有者凭据（`DATABASE_OWNER_URL`）只用于 CMS 入口脚本中的迁移与角色创建，服务启动前即从环境中移除；`heopress upgrade` 迁移时也需要 `DATABASE_OWNER_URL`。
- 安装脚本生成应用角色密码并写入 `HEOPRESS_REQUIRE_APP_ROLE=true`：启动时检查服务自身的数据库连接（`app-role --check`），不通过则拒绝启动。
- 未设置 `DATABASE_OWNER_URL` 的现有部署保持原行为（以所有者连接），并输出警告；升级前请按安装文档的“数据库角色”一节配置。
- 已知问题：行级安全（RLS）策略尚未包含在默认迁移中，应用角色本身并不意味着 RLS 已生效。

数据库中断时的修复：

- PostgreSQL 连接中断时 `cms-worker` 不再崩溃。`postgres` 3.4.9 带补丁（`patches/postgres@3.4.9.patch`）：连接已关闭的保留连接与事务拒绝后续语句，
  不再写向已断开的套接字；数据库恢复后进程继续工作。
- 数据库不可达时 `/health` 在约 1 秒内返回：经过 PostgreSQL 的探针（数据库、迁移、扩展、缓存、队列）各有 1 秒预算，超时即判为不健康
  （`/health` 返回 200 degraded，`/health/ready` 返回 503），不再超出容器健康检查的 3 秒。
- `heopress upgrade` 的 `HEOPRESS_UPGRADE_SERVICES` 默认值改为 `cms cms-worker site-classic`（Compose 服务名）。旧默认值 `cms worker site`
  与 Compose 服务名不符，切换步骤会失败；显式设置了该变量的部署不受影响。

## English

HeoPress is an AI-native open-source CMS for networks of 10–100 sites on their own domains. v1.0.0 is the first stable
release: one instance runs many sites, ingestion, translation, rewriting and the quality gate are done by deterministic
pipelines and governed AI, and external agents connect over MCP, authorized per user and per site. HeoPress is a hard
fork of LumiBase (Apache-2.0); see `UPSTREAM.md`.

Documentation entry point: `docs/en/guides/index.md` (user, developer and operations guides).

### Highlights

- **Site network**: many sites on their own domains in one instance; per-site preset collections, language, time zone,
  per-collection permalinks, redirect import and editorial profile; domain verification and on-demand TLS; translation
  groups and hreflang across sites and domains; uniform labelling and disclosure of sponsored content.
- **Studio**: an admin interface in the Carbon design with eight modules (Overview, Content, Sites, SEO / GEO,
  AI traffic, Audit, Logs & monitoring, Settings), in Chinese and English; a three-column article editor, a review
  workspace and signed previews.
- **Rendering**: the Classic engine (one process serves every site, runtime Liquid themes in a sandbox, versioned
  publishing and rollback, three starter themes); the Astro static engine, deployable to your own server,
  Cloudflare Pages, Vercel or Netlify; Git snapshots.
- **SEO / GEO**: canonical, hreflang, JSON-LD, sharded sitemaps, `llms.txt`, Markdown copies, IndexNow, an AI crawler
  policy; site audit, internal link graph, change-impact preview, AI traffic analytics.
- **Ingestion**: RSS / Atom, sitemap, list-page and URL sources; source licences and permitted uses; robots.txt,
  per-host rate limits and SSRF protection; a fallback chain of external crawl services; exact and near-duplicate
  detection and same-event clustering.
- **AI pipeline**: block-level translation and incremental retranslation, rewriting, writing; the quality gate;
  automatic publishing by trust level with veto windows and a publishing cadence; a per-call ledger, site budgets,
  rate limits and circuit breakers; a prompt workbench.
- **Agent collaboration**: the MCP endpoint (OAuth 2.1, personal access tokens, grants per site and tool group); batch
  operation plans with human approval; content branches and conflict-aware merges; six official Skills; Studio and
  IM / webhook notifications.
- **Extensions**: the Extension SDK (Apache-2.0), a capability sandbox with administrator approval and signed bundles
  only; content, runtime and pipeline extension points and veto-only pre-publish hooks; the glossary reference plugin;
  a general import bundle with the Astro site importer and URL comparison.
- **Operations**: one-command installation; built-in backups (full + incremental, SHA-256 manifests, encryption,
  retention, weekly restore drills) and single-site export; `heopress upgrade` (rehearsal, write freeze, final backup,
  restore on failure); data retention and the deletion ledger; plugin codemods.

### Requirements

- One VPS (Ubuntu 24.04 + Docker Compose); at least 2 vCPU / 4 GB.
- PostgreSQL 18 (the official database image includes pgvector and zhparser); Node.js 24 (to build from source).
- Redis, MinIO, MeiliSearch and imgproxy are not required.

### Migrating from LumiBase

- Packages `@lumibase/*` are now `@heopress/*`, and the environment prefix `LUMIBASE_*` is now `HEOPRESS_*` (the old prefix stops startup); the `lumibase_` prefix of database identifiers is kept.
- The upstream Cloudflare Workers runtime has been removed; only VPS / Docker is supported.
- Breaking plugin API changes: run `heopress-ext codemod --only lumibase-to-heopress` to convert package names, the manifest file name and the `compatibleWith` field automatically; everything else is reported as a manual step.
  Plugins now use the capability sandbox: the former `db:read`, `db:write`, `env:read` and similar capabilities no longer exist.

Database roles (security review S-5):

- In the Docker deployment the CMS and the worker connect as the non-owner application role `heopress_app`, and the
  rendering service as `heopress_render`. The owner credentials (`DATABASE_OWNER_URL`) are used only for the migrations
  and role setup in the CMS entrypoint and are removed from the environment before the server starts; `heopress upgrade`
  also needs `DATABASE_OWNER_URL` for its migrations.
- The installer generates the application role's password and sets `HEOPRESS_REQUIRE_APP_ROLE=true`: at startup the
  server checks its own database connection (`app-role --check`) and refuses to start if the check fails.
- Existing deployments without `DATABASE_OWNER_URL` keep the previous behaviour (an owner connection) and log a warning;
  configure the roles as described in the install guide's "database roles" section before upgrading.
- Known issue: the row-level security (RLS) policies are not yet part of the default migrations, so connecting as the
  application role does not by itself mean RLS is in effect.

Fixes for a database outage:

- `cms-worker` no longer crashes when its PostgreSQL connection is lost. `postgres` 3.4.9 is patched (`patches/postgres@3.4.9.patch`):
  a reserved connection or a transaction whose connection has closed rejects further statements instead of writing to the dropped
  socket, and the process keeps working once the database is back.
- `/health` answers within about a second while the database is unreachable: each probe that goes through PostgreSQL (database,
  migrations, extensions, cache, queue) has a 1-second budget and counts as unhealthy past it (`/health` answers 200 degraded,
  `/health/ready` 503), well inside the container healthcheck's 3 seconds.
- The `heopress upgrade` default for `HEOPRESS_UPGRADE_SERVICES` is now `cms cms-worker site-classic` (the Compose service names).
  The old default, `cms worker site`, did not match them, so the switch step failed; deployments that set the variable are unaffected.

### Not in v1.0

WordPress import (v1.1), multi-instance high-availability deployments, a hosted cloud service, and a build-container
sandbox for third-party Astro themes. The full list is in `docs/ROADMAP.md`.
