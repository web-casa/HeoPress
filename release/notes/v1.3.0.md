# HeoPress v1.3.0

> 状态 / Status: **已发布 / released**（v1.3.0，2026-11-12）。

[中文](#中文) · [English](#english)

## 中文

### 静态站：Netlify 的 Markdown 协商

v1.2 让同一地址按 `Accept` 返回 Markdown，但 Netlify 一直标着「不支持」——因为 `_headers` 与 `_redirects` 无法按 `Accept` 变体。
这个判断对**配置**成立，但 Netlify 的 Edge Functions 是代码。现在：

- 站点启用协商且部署到 Netlify 时，产物新增 `netlify/edge-functions/negotiate.ts` 与声明它的 `netlify.toml`；
- 该函数与运行时共用同一条 RFC 9110 规则（能比较 q 值），不是只能匹配头文本；
- 页面地址与它的 `.md` 副本**两个表示都带 `Vary: Accept`**——只给 Markdown 加，会让共享缓存把 HTML 发给要 Markdown 的客户端；
- Markdown 表示带 `text/markdown; charset=utf-8`、`X-Robots-Tag: noindex` 与指向页面自身的 canonical `Link`；
- 非协商地址、非 GET/HEAD 请求原样放行；HEAD 与 204/304 不返回 body；
- 没有协商规则时不生成任何文件，`_headers` 与 `_redirects` 与原来**逐字节相同**。

能力矩阵里 Netlify 的 `markdown-negotiation` 由 `no` 改为 `yes`，同时在注里写明代价：必须打包 Edge Functions、
生成的 `netlify.toml` 必须生效，并受 Netlify 的调用数 / 每请求 50 ms CPU / 20 MB 包体限制。

部署后的验证方式（文档里也写了）：

```bash
curl -sI -H 'Accept: text/markdown' https://example.com/2026/10/hello/ | grep -iE 'content-type|vary|link'
# 期望 text/markdown、Vary: Accept、Link: <…/hello/>; rel="canonical"
curl -sI -H 'Accept: text/html' https://example.com/2026/10/hello/ | grep -i vary   # 也必须是 Vary: Accept
```

CI 能证明的是「给定平台、路径与 `Accept`，生成的规则会发哪个文件」（回放器在 `node:vm` 中执行生成的函数，
并要求 `netlify.toml` 确实声明了它）；**平台自身是否执行**仍需上面的冒烟验证。

### 修复

`theme-pool` 的慢启动用例原本是 800 ms 加载 / 300 ms 超时，在繁忙的 runner 上会因**渲染**超时而失败——它要证明的
「启动时间不计入渲染时间」其实没被违反。改为 2 s 加载 / 1 s 超时，性质不变而余量更足。

## English

### Static targets: Markdown negotiation on Netlify

v1.2 made a page answer Markdown at its own address when `Accept` prefers it, but Netlify stayed marked unsupported:
`_headers` and `_redirects` cannot vary on `Accept`. That was true of configuration, not of Netlify's Edge Functions,
which are code. Now a site with negotiation enabled deploys `netlify/edge-functions/negotiate.ts` and a `netlify.toml`
that routes it:

- the function shares the runtime's RFC 9110 rule (it compares q-values, it does not just match header text);
- both representations of a negotiable page carry `Vary: Accept` — adding it only to Markdown would let a shared cache
  serve HTML to a client that asked for Markdown;
- the Markdown answer carries `text/markdown; charset=utf-8`, `X-Robots-Tag: noindex` and a canonical `Link` to the page;
- non-negotiable addresses and non-GET/HEAD requests pass through untouched, and HEAD or a null-body status never
  carries a body;
- no rules means no files, and `_headers` / `_redirects` stay byte-identical.

The capability matrix moves Netlify's `markdown-negotiation` from `no` to `yes`, with the cost stated in the note:
Edge Functions must be bundled, the generated `netlify.toml` must be honoured, and Netlify's invocation, 50 ms CPU per
request and 20 MB bundle limits apply.

CI proves which file the generated rule serves for a given platform, path and `Accept` (the replay harness executes the
generated function in `node:vm` and requires the `netlify.toml` declaration). Whether the platform itself runs it is
still verified by the post-deploy `curl` check in the docs.

### Fixed

The `theme-pool` slow-start test used an 800 ms load against a 300 ms render timeout, so a loaded runner failed it by
slow **rendering** — the property it proves (start-up is not counted as render time) was never violated. It now uses a
2 s load against a 1 s timeout: same property, far more headroom.
